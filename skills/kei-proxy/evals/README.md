# kei-proxy evals

Eval cases for the kei-proxy skill (runtime proxy executable for governed decisions).

## Running

Checks are deterministic (case-insensitive string checks in `evals.json`, no
LLM grader). The CI gate (`.github/workflows/agent-evals.yaml`) runs every
case once per model profile on a pull request and 3 times in the nightly
sweep of `main`, with the profile's fixed sampling and seed, and gates on the
average pass rate (threshold 0.90). To reproduce the nightly run locally:

```bash
node scripts/run-evals.mjs --skill kei-proxy --harness opencode \
  --model-profile glm-5.3-flash --repeats 3 --jobs 1 \
  --out evals-out/kei-proxy-glm-$(date +%F)
node scripts/run-evals.mjs --skill kei-proxy --harness opencode \
  --model-profile qwen3.8-27b --repeats 3 --jobs 1 \
  --out evals-out/kei-proxy-qwen-$(date +%F)
```

`evals-out/` is ignored by git. Don't commit local benchmark results; the CI
gate's report is the record.

## Cases

Case 7 checks connector availability against the installed runtime and bundle, and teaches fail-closed denial reasons without relying on stale release claims.

Case 9 covers the daemon socket client as primary, tool registration through `POST /v1/tools:register`, the `kei harness sync --manifest` alternative, and the CLI fallback.

Case 8 covers what `kei-proxy hook claude` records for a failed call and an asked call (the `failed` flag, `decision` and `permission_reply` events), that the hook never answers a permission prompt, and which versions it needs.

Cases 14 and 15 cover the model routes on the `kei-proxy serve` socket: `GET /v1/model-config`, `GET /v1/models` and `GET /v1/model-profiles`, and no `POST /v1/chat/completions` (the harness calls the model itself).

## Widened checks and their negative tests

These checks use a regex or a widened phrase list. Each entry below gives
the final pattern, answers it accepts, and wrong answers it rejects.
`run-evals` grades with the same case-insensitive matching. This section
was generated by running each string against the pattern in `evals.json`.

### Case 14: The response says the daemon has no chat completions route.

Shared no-chat-route pattern for cases 14 and 15.

```text
(no|not|n.t|never)[^.\n]{0,60}(/v1/)?chat/completions|chat/completions[^\n]{0,80}(not served|isn.t served|is not served|does not serve|doesn.t serve|404|does not exist|doesn.t exist|removed|no such)|(no|not|n.t)[^.\n]{0,40}(serve|expose|have|provide)[^.\n]{0,40}chat|\bno\b[^.\n]{0,30}chat[^.\n]{0,30}(route|endpoint)
```

Accepts:

- `` kei-proxy serve has no POST /v1/chat/completions route `` → match
- `` The daemon does not serve chat completions `` → match
- `` POST /v1/chat/completions returns 404 on the socket `` → match

Rejects (wrong answers):

- `` Use POST /v1/chat/completions on the socket `` → no match
- `` Send your chat completions to the socket `` → no match
- `` kei-proxy proxies chat/completions to the provider `` → no match

### Case 14: The response says the harness calls the model itself.

Tightened when written: a bare `directly` alternative was removed so "directly via kei-proxy" cannot pass.

```text
(calls?|calling|send|sends|POSTs?) (the )?(model|provider)[^.\n]{0,40}(itself|directly|yourself)|harness[^.\n]{0,60}(calls?|POSTs?|sends?)[^.\n]{0,40}(model|provider)|(model|provider) directly
```

Accepts:

- `` the harness calls the model provider itself `` → match
- `` call the provider directly with the endpoint from model-config `` → match

Rejects (wrong answers):

- `` directly via kei-proxy `` → no match
- `` kei-proxy calls the provider for you `` → no match
- `` send it through the socket `` → no match
